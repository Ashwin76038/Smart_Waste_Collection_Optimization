# Phase 3 business-question SQL

Run `python 06_python/scripts/run_sql_analytics.py` from the project root. It executes the 14 named, read-only queries in `phase3_business_questions.sql` against the Phase 2 DuckDB database, saves bounded CSV results to `14_outputs/tables/phase3_sql/`, and verifies fact/mart counts and arrival-volume reconciliation. Every exported operational table is labelled `data_origin=synthetic`; the query manifest records row counts and schema.

Questions cover per-bin-normalized zone generation, gross arrival rate, overflow frequency, ward-level and bin-level service timing, local-hour demand, daily lag/lead and seven-day trend, weekday pattern, service frequency, route proxies, local anomaly flags, monthly seasonality and reconciliation. The SQL deliberately uses WHERE, ORDER BY, GROUP BY, HAVING, JOIN, CASE, subqueries, CTEs, window functions, RANK, LAG, LEAD, rolling averages, date functions and `QUANTILE_CONT` for business purposes.

Definitions: `generated_kg_simulated = arrivals_l_simulated × 0.12 kg/L` is a scenario mass conversion, **not** officially measured city waste. `gross_capacity_pct_day` is generated litres divided by capacity and days; it can exceed 100% and is not a sensor fill percentage. Overflow uses latent physical simulation truth, since observed sensors clip fill at 100%. “Early” means a successful attempt with latent pre-service fill under 35%; “late risk” means at least 95% latent pre-service fill or positive overflow in that slot. These thresholds are exploratory flags, not adopted service standards. Vehicle distance is mechanically assigned and cannot establish route inefficiency. Anomalies are deviations from each zone's previous 28 days and need investigation, not causal labels.

`timestamp_utc` is converted to Chennai local time by adding 5 hours 30 minutes. The scenario is fixed to 2026 and assumes no DST. Current GCC ward identifiers are used only as geographic grouping. Census 2011 native ward rows are never joined by ward number. SQL tables may contain `simulation_truth` only for retrospective diagnostics; future live decision features must remain within the observed-only fact and information available at decision time.
